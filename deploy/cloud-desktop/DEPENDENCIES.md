# Linux dependency and source receipts

These files support a compatibility trial. The Linux requirements candidate began from the pinned upstream direct requirements and was corrected using actual package metadata and resolver results. `requirements-linux.resolved.lock` is the reviewed hashed Linux input used by the image builder; 110 packages installed and passed package/import checks on the supplied pod. Actual CUDA baseline probes and native inference passed, while a sustained session exposed GPU memory growth. A local emulated amd64 image passed CPU desktop, SSH and volume recreation checks; fresh GPU image, optional-feature and full client acceptance remain separate gates. `sources.lock.toml` records their scope. `bootstrap-linux.lock` pins the verified Linux x86_64 uv 0.8.22 wheel and SHA256 from [its PyPI release](https://pypi.org/project/uv/0.8.22/).

The first fresh Linux resolution on 5 October 2026 failed before application package installation: upstream `cuda-toolkit==13.2.1` contradicts the `cuda-toolkit[cublas]==13.0.2` requirement of `torch==2.11.0+cu130`. The Linux requirements now use 13.0.2 and resolve NVIDIA leaf packages from compatible metadata, preserving native-facing framework versions. Upstream pyqtdarktheme 2.1.0 rejects Python 3.12; the drop-in `pyqtdarktheme-fork==2.3.6` supplies the same import API. ORT's exact CUDA13 cp312 Linux wheel URL/SHA256 avoids ambiguous same-version selection across indexes. No `--no-deps` workaround or borrowed-runtime mutation was used.

`gpu-env.sh` discovers actual installed NVIDIA/TensorRT library directories before launching Python and retains injected host-driver paths. ORT 1.26 still searches an older wheel layout automatically. Preflight checks the optional lazy TensorFlow import in a child: eagerly loading it before ORT reproducibly crashed CUDA session creation, whereas the native baseline order executes CUDA correctly. This isolation is recorded in receipts and does **not** validate TensorFlow mouth-feature coexistence. See the detailed [validation record](../../docs/cloud-desktop-validation.md).

The installer targets Ubuntu 24.04 x86_64 and Python 3.12. It installs desktop/Qt/media system libraries through apt and application packages in an isolated venv. `install.sh check` is read-only. `install.sh install` never starts services; the caller starts `entrypoint.sh` separately after reviewing setup/import evidence.

For an existing pod, `--skip-apt --borrow-python /absolute/existing/venv/bin/python --skip-models` stages only the pinned application and persistent mappings and runs import checks. It never installs into the borrowed runtime. The receipt identifies this as a borrowed compatibility environment, lists its actual packages, and does not assert conformity to CUDA 13 dependency pins. `FUSION_RUNTIME_ROOT=/opt/fusion-runtime` instead places a new venv and package cache on ephemeral container disk; reinstalling that runtime after pod replacement is required. Keep projects, native state, references and model assets under `/workspace/fusion`.

RunPod volume quota must be checked through actual storage usage/quota evidence. `df` may show the underlying network storage capacity rather than the allocated volume quota. The local storage probe labels `backing_filesystem_free_bytes` accordingly and cannot prove quota headroom from that capacity report. Never copy or download the complete catalog without checking quota and using available verified model links. An optional operator observation, `FUSION_VOLUME_QUOTA_FREE_GB=18 FUSION_VOLUME_QUOTA_CHECKED_AT=2026-10-05T12:00:00Z`, caps minimum-space checks and new model reservations. This is a static upper bound, not a dynamically authoritative measurement: other writers and new allocations can reduce it. New download payload bytes are deducted in `receipts/quota-consumption.json`; repeat invocations retain that deduction for the same declared bound/time. A fresh provider quota check and a new observation timestamp are required to refresh the bound. Unknown download sizes fail closed when this cap is enabled. Verified links need no new weight payload reservation.

The image and desktop entrypoint default to the eight tested native models: `RetinaFace,Inswapper128ArcFace,Inswapper128,FaceLandmark5,FaceLandmark68,FaceLandmark106,GFPGANv1.4,CodeFormer`. The entrypoint applies this default only when `FUSION_MODEL_SELECTION` is unset; an explicit operator selection, including `all`, is preserved. Before enabling downloads, verify real volume quota and reuse inventory. Catalog-wide downloads require explicit `FUSION_MODEL_SELECTION=all`; they are not an image default. Other selected native features still need their own catalog weights.

Use `--reuse-model-root /absolute/existing/model_assets --models RetinaFace,Inswapper128ArcFace,Inswapper128,FaceLandmark5,FaceLandmark68,FaceLandmark106,GFPGANv1.4,CodeFormer` during installation to hash and reuse these weights. Reuse prefers hardlinks, records cross-volume symlinks, and never replaces existing mismatched assets or reference KV data. The separate installer accepts an explicit `--models all` for a reviewed full-catalog installation; use `--skip-models` when the runtime weights are already staged and verified.

Run `install.sh install --resolve-lock` on the intended Linux environment to generate `receipts/requirements-linux.resolved.lock` with transitive pins and hashes and then install with hash verification. `--resolve-only` stops after compilation and writes `receipts/resolution.json`; it stages source and prepares isolated Python/uv bootstrap but installs no application packages, maps no native state, downloads no models and starts no services. For fast iterations, call `uv pip compile --generate-hashes` directly against the existing separate runtime, retaining the same explicit indexes and source input; no installer rerun is necessary. Install a reviewed/promoted result with `--resolved-lock /path/reviewed-hashed.lock`, which consumes it without fresh compilation. Resolution flags cannot be combined with a read-only borrowed runtime. This follows [uv's documented compile/sync workflow](https://docs.astral.sh/uv/pip/compile/). The upstream NVIDIA, Torch CUDA 13 and ORT nightly indexes are explicit; their artifacts and exact origins still need review before promoting the generated lock. Copy the validated lock into the repository only after confirming imports, loaded CUDA libraries, real Torch/ORT work, representative native models and selected encoding. The multiple-index strategy currently matches upstream `unsafe-best-match`; it is described in [uv's index documentation](https://docs.astral.sh/uv/configuration/indexes/).

Setup writes `receipts/setup.json`, the resolved lock where requested, `receipts/pip-freeze.txt` for newly installed runtimes, and `receipts/python-path.txt`. The setup receipt contains source commit/overlay hash, the verified code manifest hash, exact installed Python/system package versions, FFmpeg identity, dependency status and known image/base identity. Secrets are excluded. For a borrowed environment, package inventory is recorded through Python metadata rather than installing pip into that environment.

`--source-patch /path/reviewed.patch` applies an explicit patch to a fresh archive of the pinned commit before computing the code manifest. Repeating the same patch is idempotent. Changing overlays requires `--replace-source`, which archives the previous verified source and preserves durable state. Patches cannot modify native mapped paths, Git internals or paths outside the source tree. The exact overlay SHA256 and a persistent copy of the patch are recorded in receipts. An existing tree with changed code or unknown provenance is refused.

The Dockerfile consumes a required reviewed hashed Linux lock without resolving it again, and downloads no model weights at build time. Build with `build-image.sh --source-patch /path/reviewed-native.patch --resolved-lock /path/reviewed-linux.lock --tag fusion-desktop:pilot --receipt /path/build-receipt.json`. The explicit `--development-resolve` alternative performs fresh candidate resolution and is labelled accordingly; it is not a reproducible release build. Build cleanup removes only the newly-created image runtime uv cache/bootstrap in the same install layer; the installed venv and source receipts remain. The supplied patch must include the reviewed native persistence/encoder fixes and their new helper files. The script copies only deployment files plus that patch/lock into a temporary build context, verifies both hashes during the image build, and never pushes an image. A duplicated native diff is not tracked in this repository. The image carries the exact patch, applies it during setup and fresh runtime source staging, and rejects an existing mounted source with a different overlay. Cache identity includes the resulting source manifest/patch identity. A direct build without the required patch/lock fails unless the development resolver was explicitly selected.

For a fresh custom RunPod image, add **22** to **Expose TCP Ports**, retain a public-IP-capable instance, and use the assigned external IP/port from **Connect → Direct TCP Ports**. The external port differs from container port 22 and can change after reset. These settings follow [RunPod's port documentation](https://docs.runpod.io/pods/configuration/expose-ports) and [custom-image SSH instructions](https://docs.runpod.io/pods/configuration/use-ssh). A local tunnel is `ssh -i /path/private-key -p ASSIGNED_EXTERNAL_PORT -L 6080:127.0.0.1:6080 root@ASSIGNED_IP`; open `http://127.0.0.1:6080` in the browser. Keep raw VNC, websockify and desktop HTTP unexposed. If a recovery marker prevents startup, RunPod's basic SSH terminal remains the administration route for inspected recovery; it does not provide SCP/SFTP.

An abnormal guard exit keeps `.writer-state.json` active after releasing flock. A failed Fusion child sets `unclean_fusion` and cannot relaunch under the same desktop owner. The native source overlay validates the Fusion-only guard PID and holds `.native-instance.lock` for its entire lifetime; the launcher probes that kernel lock before setup, launch and recovery, so killing a wrapper cannot authorize another writer while its orphaned native child lives. This is cooperative protection against accidental launch, not a security boundary against arbitrary root code. Inspect the last writer, native save logs and verified snapshots, prove both guard and native process are gone, then use `runtime.py --root /workspace/fusion recover-lock --expect-token EXACT_INSPECTED_TOKEN`. Recovery refuses the same live process identity, a live native instance lock, a mismatched token or an occupied flock. Linux markers identify the owner by boot ID, PID namespace inode and process start ticks, allowing inspected recovery after container recreation even when the unrelated new entrypoint also has PID 1. Namespace inodes may be reused, so the complete identity is compared. Legacy markers without that identity conservatively retain live numeric-PID refusal. Ordinary startup never clears an active marker automatically, including when identity proves the old owner is gone.
